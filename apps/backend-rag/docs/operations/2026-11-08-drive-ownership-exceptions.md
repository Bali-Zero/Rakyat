# Drive ownership and visibility exceptions

Mandate: CRM-DRIVE-EXCEPTIONS-1108. BLUE, gear3, external Codex builder; fresh cross-family Claude exact-head gate before release. Base699533d58b7271f65dd1ecd9e6aa75eed8df935c. Owner authorized resolution of the remaining15 loose files,4 Tax archives and historical root cohorts. No identity merge, access expansion, client notification or deletion is authorized by inference.

## Observed failure and consumer

The Drive poller builds last-row-wins dictionaries from subfolder/client references, including archived clients. The reviewed historical cohort contains164 subfolder IDs associated with multiple client IDs. The poller has no exact invoice-reference exclusion: moving a billing PDF from a client root into a canonical category can create a duplicate general document with default client visibility. The metadata writer's ancestry check accepts shared roots, and the portal proxy's own-document lookup omits the visibility/deletion/archive predicates used by normal portal downloads.

## Required behavior

1. Automatic ingestion accepts a folder owner only when the underlying references establish one eligible client of a supported type (individual or company) and a nonambiguous current root. Corporate customers are supported records, often containing a person contact and company data; they are not automatically erroneous. Validate the existing physical layout rather than retyping the client. Do not silently pick a survivor among distinct client IDs, including historical references. Retain all DB records and mappings. Duplicate rows for the same owner may collapse only when their classification agrees; conflicting names/classifications fail closed. No table-wide cleanup or root reassignment.
2. Recheck the owner immediately before nested-folder registration and document insertion. If a client became archived, its root changed, or ownership became ambiguous, skip the write. Nested registration must use an actual supported conflict key and must not claim success when another folder owns that name. Keep existing document lifecycle behavior outside this change.
3. An exact billing reference in invoices.drive_file_id or practices.documents.invoice.invoice_drive_id prevents general-document ingestion. Do not use filenames to decide billing ownership. Keep the invoice generator, its root-level backup location and its failure/mail behavior unchanged: those PDFs are first-class billing-managed artifacts, not unregistered general documents. Do not invoke the mail-producing invoice flow in live QA. Changing the generator's filing policy would require its own race-safe billing-publication design and is outside this repair.
4. At metadata-registration time, reject archived client owners, incompatible existing registered ownership and ambiguous root ancestry. Do not narrow the staff read proxy. Portal file and thumbnail access to a document requires own client ID plus client_visible=true, deleted_at IS NULL and is_archived not true, matching the ordinary document download. Preserve legitimate invoice access.
5. A bounded operator-only repair command may register an already-existing Drive PDF/JPEG as a hidden document, preserving its file ID. Default is read-only; apply requires the exact reviewed plan hash, current source metadata, unique active owner, corroborated identity hashes, canonical destination and no conflicting document/company/billing/practice references. No fake intake proposal ID. Reuse the existing pure DB writer with truthful repair provenance; client_visible=false is in the INSERT, OCR is explicitly skipped, and there is no notification, OCR dispatch, upload, identity enrichment or visa-state mutation. No new public endpoint for this command. Register hidden before the coordinator moves the file so the poller cannot publish a duplicate. Failed moves leave a visible-to-staff, hidden-to-client record with truthful planned-move provenance and an idempotent recovery path, not a false completion claim.
